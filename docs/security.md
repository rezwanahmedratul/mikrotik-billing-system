# Security Architecture, Threat Model, and Hardening Guide

## Overview
This document specifies the defense-in-depth security architecture, multi-tenant isolation guarantees, cryptographic standards, authorization matrix, and operational incident response procedures for the MikroTik Billing and ISP Management Platform.

---

## 1. Multi-Tenant Isolation & Boundary Enforcement

The platform enforces strict logical multi-tenancy at the data layer, application service layer, and router gateway boundary:

| Layer | Isolation Mechanism | Verification Test |
| :--- | :--- | :--- |
| **Data Layer** | Every business entity contains a mandatory, non-nullable `tenantId` foreign key with compound unique constraints (`UNIQUE(tenantId, code)`, `UNIQUE(tenantId, accountNumber)`). | Validated in Prisma schema |
| **Service Layer** | Every read, update, delete, or provisioning operation requires a verified `tenantId` parameter originating from the authenticated session token. Queries cross-reference `where: { id, tenantId }`. | `src/common/security.test.ts` (Cross-Tenant Penetration) |
| **Audit Trails** | Audit queries filter strictly on `tenantId`. A tenant administrator cannot query, inspect, or correlate events generated by another tenant organization. | Validated in `security.test.ts` |
| **Router Hardware** | RouterOS API/REST credentials are scoped per-tenant. A tenant cannot discover, target, or execute provisioning commands on a gateway owned by another ISP. | Validated in `security.test.ts` |

## 2. Cryptographic Architecture & Key Management

### Credentials at Rest
- **Router Passwords & PPPoE Secrets**: Encrypted using authenticated AES-256-GCM (`packages/shared/src/encryption.ts`).
- **Ciphertext Format**: Stored as `iv:tag:ciphertext` in hexadecimal encoding.
- **Key Derivation & Verification**: Derived from a 32-byte master encryption key (`ENCRYPTION_KEY`). If the key length is invalid, the encryption layer immediately throws a fatal exception rather than fallback to insecure ciphers.
- **Output Redaction**: Public and internal API responses redact all sensitive secrets. Subscriber responses return boolean flags (`hasPassword: true`) without leaking plaintext or raw cipher strings.

### User Passwords
- Hashed using **Argon2id** (memory cost 64MB, time cost 3 iterations, parallelism 1), resistant to GPU/ASIC cracking.
- Raw passwords are never logged, echoed in errors, or stored in plaintext.

### Webhook Signatures
- Provider callbacks (bKash, Nagad, Stripe) enforce cryptographic HMAC-SHA256 signature verification over the raw incoming HTTP request body.
- Invalid or missing signatures return `400 Bad Request` or `401 Unauthorized` before parsing payload data.
- Replayed callbacks with identical event IDs are deduplicated idempotently via `PaymentProviderEvent` unique indexes without double-crediting invoices.

## 4. Network Exposure & RouterOS Least Privilege

### Infrastructure Hardening
- **Localhost Port Binding**: Development and staging Docker Compose files bind PostgreSQL and Redis to `127.0.0.1` (`127.0.0.1:5432:5432`, `127.0.0.1:6379:6379`), preventing exposure on public network interfaces.
- **Micro-Segmentation**: Background workers communicate with RouterOS management ports (REST 443 / API-SSL 8729) over dedicated VPN/management subnets.

### Safe Router Change Automation
- **Safety Boundaries**: The Guided PPPoE Setup engine and service lifecycle automator only manipulate:
  - `/ip/pool` (client allocation range)
  - `/ppp/profile` (bandwidth rate-limit profiles)
  - `/interface/pppoe-server/server` (service listener interface)
  - `/ppp/secret` and `/ppp/active` (account credentials & session drops)
- **Zero Touch on Critical Infrastructure**: Wan uplinks, default routing tables, firewall NAT tables, and core system users are strictly excluded from automated write access.

## 5. Operational Incident Response & Runbooks

### 1. Compromised Staff Credential
1. **Immediate Revocation**: The tenant administrator opens **Staff Management** (`/dashboard/staff`) and toggles the compromised user status to `Inactive` or changes their password.
2. **Session Invalidation**: All active JWT refresh sessions for the user ID are revoked.
3. **Forensic Audit**: Filter the audit trail (`/dashboard/reports` -> Audit Trail) by `userId` to inspect all actions executed during the compromise window.

### 2. Router Credential Rotation
1. Generate a new strong random password (minimum 20 characters).
2. Update the router user credential on the physical RouterOS device (`/user set billing_api password=...`).
3. Update the credentials in the Platform Console (`/dashboard/routers` -> Edit Gateway).
4. Run "Test Handshake" to confirm immediate encrypted reconnection without service downtime.

### 3. Master Key (`ENCRYPTION_KEY`) Rotation
1. Generate a new 256-bit AES key.
2. Run the platform re-encryption script (`scripts/rotate-keys.ts` or automated migration) to decrypt existing records with the old key and re-encrypt with the new key in a single transactional batch.
3. Deploy the updated `ENCRYPTION_KEY` environment variable.
